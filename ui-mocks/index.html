Each tab has its own cooldown, so this stays five timers The five countdowns are not one clock shown five times. Each tab caches under its own key (interfaces, links/ports, ip_addresses, vlans, inventory) and computes cache_expiry at its own fetch time, so refreshing one tab does not reset the others. All five tab panes are also in the DOM at once, only one carrying show active, so the five ids and five intervals have to stay. The coloured bar on each tab above comes from the same per-tab cache state. What can be shared is the markup: one include, rendered once per tab with that tab's own expiry and id, placed in the header row. That fixes the position without touching the timers. One thing to settle first: the countdown currently sits inside the content fragment, which is exactly the element each tab's Refresh replaces. The header row is outside that target, so moving it there means a refresh stops repainting it. It needs an out-of-band swap, or the header brought inside the swap target.

Trade-offs, briefly A keeps everything on one screen and needs no new template file; the panel is cramped on a narrow window. B has room to explain each option, at the cost of a dialog in front of a routine action. C matches an existing pattern on the same tab, but reintroduces the vertical shift when open. All three keep the same field names (auto_select_lag_members, exclude_columns), so the POST payload does not change. The badge count is the part that matters whichever is chosen: without it, a non-default exclude becomes invisible, which is worse than today's clutter.
